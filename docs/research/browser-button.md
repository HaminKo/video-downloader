# Browser button: getting a link from the browser into the app

Researched 2026-11-13 for To do 10. Each point says whether it was measured on this PC, comes from a source, or is general knowledge (not checked). On this PC (read from the registry, `...\BLBeacon`): Chrome 156.0.8078.80, Edge 157.0.4341.46. The user mostly uses Chrome (user, 2026-11-13); the to-do was first written for Edge.

Two ways were looked at: (A) an extension with native messaging, (B) a bookmarks-bar button (a `javascript:` bookmark, "bookmarklet") that opens a link type of our own (`video-downloader:`) registered in Windows. Both need the same last part: a started program handing the link to a window that is already open (see "Hand-over to the open window").

## A: extension + native messaging
- **Host manifest** (sources: [Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging)): JSON with `name` (lowercase letters, digits, `_` and `.` only), `description`, `path`, `type: "stdio"`, `allowed_origins` (`chrome-extension://ID/`, no wildcards). On Windows `path` may be relative to the manifest's folder. The manifest can be anywhere; a registry key's default value holds its full path: Chrome `HKCU\Software\Google\Chrome\NativeMessagingHosts\NAME`, Edge `HKCU\Software\Microsoft\Edge\NativeMessagingHosts\NAME`. Edge falls back to Chrome's key when it has none of its own, so Chrome's key serves both.
- **How Chrome starts the host** (source: Chromium's [launch_context_win.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/extensions/api/messaging/launch_context_win.cc), main branch, read 2026-11-13): an `.exe` is started directly, anything else (a `.bat`) through `cmd.exe`; hidden (`start_hidden`), in the host's own folder. No job object is set in that code, so a window the host starts should outlive the host and Chrome (inferred from the code, not tested).
- **Protocol** (same sources): each message is UTF-8 JSON preceded by a 32-bit length in native byte order; at most 1 MB from the host. On Windows stdin and stdout must be in binary mode. The first argument is the caller's origin; on Windows also `--parent-window=N` (0 from a service worker). `sendNativeMessage` starts a new host process per message; the host's first reply goes to the callback.
- **Extension ID:** without a `key` in manifest.json, an unpacked extension's ID comes from its folder path; with a `key` (a public key) it stays fixed. Source: [Chrome docs, manifest key](https://developer.chrome.com/docs/extensions/reference/manifest/key) and a Chromium DevRel reply in [chromium-extensions](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/Su50pbNzRms).
- **Developer-mode warning, Chrome:** gone. Chromium deleted its developer-mode bubble (`DevModeBubbleDelegate`) on 2023-11-28 ([commit 863d57a08c](https://github.com/chromium/chromium/commit/863d57a08c), "Remove ExtensionMessageBubbleController"); its commit position (1230260) puts it in about Chrome 121 (estimate). Not checked by hand in Chrome 156.
- **Developer-mode warning, Edge:** Edge shows its own notification while an unpacked extension is loaded, and it can't be turned off. Source: [Microsoft support](https://support.microsoft.com/en-us/edge/developer-mode-extension-notification) ("we don't allow dismissing the notification"); a [Microsoft Q&A thread](https://learn.microsoft.com/en-us/answers/questions/1360814/disable-developer-mode-extension-notification-ms-e) (2023) reports it at every start. So this way suits Chrome, not Edge.
- **Store instead:** publishing to a store avoids all of this, but needs a developer account and a review; too much for a one-person tool (judgement, not researched further).

## B: bookmarks-bar button + `video-downloader:` link type
- **The browser's prompt:** opening a link type registered in Windows makes the browser ask first, with an "Always allow" checkbox remembered per site and link type. Edge: shown by default since Edge 84 (source: [Edge policy ExternalProtocolDialogShowAlwaysOpenCheckbox](https://learn.microsoft.com/en-ie/deployedge/microsoft-edge-browser-policies/externalprotocoldialogshowalwaysopencheckbox)); a 2020 forum post says only on https pages. Chrome: the same checkbox (general knowledge, not checked).
- **Registering the link type** (general knowledge, not checked): `HKCU\Software\Classes\video-downloader` with a `URL Protocol` value and `shell\open\command` = the command, `%1` standing for the whole link. No admin rights needed under HKCU. Works in every browser.
- **Bookmarklets on YouTube:** YouTube enforces Trusted Types, which blocks setting HTML from strings ([Chrome blog](https://developer.chrome.com/blog/trusted-types-on-youtube)). A [dev.to post](https://dev.to/erysngl/how-i-bypassed-youtube-musics-csp-to-stop-those-annoying-video-paused-popups-3ohf) describes a bookmarklet that ran on YouTube Music once it avoided `innerHTML`, so a bookmarklet that only sets `location.href` should run. Not checked.
- Chrome shows the bookmarks bar only on the New Tab page unless it's set to always show (Ctrl+Shift+B) (general knowledge).

## Hand-over to the open window
- **Named pipe (measured 2026-11-13, Python 3.13.1, scratch script):** `multiprocessing.connection.Listener(r"\\.\pipe\NAME", family="AF_PIPE")` with `send_bytes`/`recv_bytes` (never `send`/`recv`, which unpickle and so run whatever a sender packs in) passed a link in 1.7 ms. A second Listener on the same name raises `PermissionError` (WinError 5), so a second window can tell that one is already listening. `Client` with no window listening raises `FileNotFoundError` (WinError 2). Web pages can't reach a named pipe, unlike a localhost port.
- **pythonw (measured 2026-11-13):** started without a console, `sys.stdout` and `sys.stderr` are `None`; `print(..., file=sys.stderr)`, `traceback.print_exc()` and a yt-dlp warning then do nothing and don't fail. So the window can be started without a console; the details the app prints are lost then.
- **Bringing the window to the front** (general knowledge, not checked): Windows lets a program take the foreground only in some cases, for example when it was started by the program in front. The started program can pass that right on with `AllowSetForegroundWindow` before handing over the link. If it doesn't work, Windows flashes the taskbar button instead.
  - Measured 2026-11-13 (step A, scratch script, once): a window opened by `pythonw` from a process that wasn't in front (Claude's shell, Chrome in front) did come to the front. A link sent to a window that is open but behind another one: not measured (it would take the user's screen again); the user's hand test covers it.
- **Other PCs** (general knowledge, not checked): `multiprocessing` creates the pipe with Windows' default rights, which let only the same user (and admins) write to it; another PC on the network would need this user's sign-in. Found by the review of step A; no change made.
- **Review of step A (2026-11-13), left as they are:** a program that connects and never writes would block the window's listening (only a misbehaving local program could); a link sent in the very moment the window closes is lost; a second window opened without a link doesn't listen, and doesn't take over when the first one closes (a candidate for a Someday to-do: starting the app again brings the open window to the front); during a running download the "Link received" hint is replaced by the next progress report; text with line breaks inside goes into the box as it is.

## Downloading from Chrome (To do 16, step A, 2026-11-14)
- **JSON on the pipe:** `json.loads` of 60,000 nested `[` raises `RecursionError`, not `ValueError` (measured, Python 3.13.1): with only `except ValueError` it would have ended the window's listening thread (and the helper without a reply, as the review of step B noted). handoff.py and host.py catch both. A plain-text link (the format before To do 16) is dropped by a window from now on; a window still running the old code would put a JSON message into its box as text, so the app is restarted once after the update.
- **The helper's command line:** `pythonw -m video_downloader --download KIND --quality Q [--subtitles] -- LINK`. Python 3.13's argparse reads the link after `--` into the optional positional argument (measured, all three cases); `--` keeps a link from ever counting as an option.
- **Starting minimized:** `root.iconify()` on a new `tk.Tk()` before `mainloop()` gives `state() == "iconic"` after one `update()` (measured): the window opens on the taskbar only.
- **Review of step A (2026-11-14, code-review skill, medium).** Fixed: `"start": null` counted as no choices (a link alone, to the front) instead of being refused; `send()` let the window to the front for a download too. Left as they are (no case seen): two downloads sent within the second or two a window takes to start listening open two windows that download side by side, and the one that saves last writes history.json without the other's new rows (the Someday candidate above, now with more at stake: a Someday to-do was proposed); a window still running the code from before To do 16 misreads the JSON (restart it once); `json.dumps` escapes non-ASCII, so a link of thousands of non-ASCII characters could pass the 64 KB limit (Chrome's links are percent-encoded); `--quality` and `--subtitles` are ignored without `--download mp4`, as the window greys them out for MP3; host.py checks the link twice (`web_link()`, then `checked_message()`) to tell "not a web page" from "unknown choices", and decodes JSON itself to tell a broken message from those.

## Building the button (step B, 2026-11-14)
- **Extension ID from the `key`** (source: Chromium [components/crx_file/id_util.cc](https://github.com/chromium/chromium/blob/main/components/crx_file/id_util.cc), main branch, read 2026-11-14): `GenerateId` takes the SHA-256 of the key's bytes (the base64-decoded `key`, a DER public key), hex-encodes its first 16 bytes and writes the digits 0-f as the letters a-p. Chrome's [manifest key page](https://developer.chrome.com/docs/extensions/reference/manifest/key) doesn't say how (checked). The key is an RSA 2048 key made with Git for Windows' `openssl` 3.5.9 (`genrsa`, then `rsa -pubout -outform DER`, then base64); its private half was deleted, since an unpacked extension is never signed. Its ID: `ihppdkclbgnohioighdlmologiiggoah` (`browser.EXTENSION_ID`; tests/test_browser.py recomputes it from extension/manifest.json). That Chrome shows the same ID: the user's hand test.
- **Binary stdin and stdout (measured 2026-11-14, Python 3.13.1):** the bytes `\n`, `\r\n` and Ctrl+Z (`\x1a`, which ends a text-mode read) pass through `sys.stdin.buffer` and `sys.stdout.buffer` unchanged, both when Python is started directly and through `cmd.exe /d /s /c` running a `.bat`. So Python already opens them in binary mode on Windows; host.py doesn't call `msvcrt.setmode`. A test runs host.bat through cmd.exe with a 26-byte (Ctrl+Z) message.
- **The `.bat`'s `@` (measured 2026-11-14):** without it, cmd.exe echoes the command line onto stdout before the reply (the test then fails with `b'\r\nc:\\...'` where the length should be), which would break the first message Chrome reads.
- **Running a `.bat` through cmd.exe from Python (measured 2026-11-14):** `subprocess.run(["cmd.exe", "/d", "/s", "/c", '"path.bat"'])` gave no output at all: the list form escapes the quotes with backslashes, which cmd.exe doesn't understand. A single command-line string works.
- **Why the helper is its own module (measured 2026-11-14, 3 runs):** importing `handoff` takes 0.03-0.09 s, importing `downloader` (yt-dlp) 0.18-0.37 s more. host.py imports only `handoff`; browser.py (setup, run once) uses `downloader.DATA_FOLDER`.
- **The window the helper opens:** `pythonw -m video_downloader LINK`, with `DETACHED_PROCESS`, no console, and stdin, stdout and stderr set to `DEVNULL`, so it holds none of Chrome's pipes. Whether it stays open when Chrome closes: the user's hand test.
- **Chrome's old PATH (found in the user's hand test, 2026-11-14):** a window opened by the button said "ffmpeg is missing" on Download. Measured: Chrome's browser process had been running since 2026-11-04, before ffmpeg and Deno were installed (2026-11-10), while the user's PATH in the registry (`HKCU\Environment`) holds both folders. The helper and the window it starts inherit Chrome's environment, so their PATH was 10 days old. A program's environment never updates by itself; Explorer rereads the registry when told, Chrome doesn't (general knowledge). Fix: `host.fresh_path()` rebuilds PATH from the registry (the system's part, then the user's, `%...%` expanded), as a newly started program gets it, and `start_window` passes it to the window; it finds both ffmpeg and Deno on this PC (measured). This also covers an ffmpeg update through winget later: the folder's name holds the build (`ffmpeg-N-127043-...`), so an update likely changes it (not checked). Rejected: only telling the user to restart Chrome completely, which works too but has to be redone after every ffmpeg update, while Chrome runs for days.
- **Icons:** a white down arrow over a bar on a blue rounded square (`#2563eb`), drawn at 8x with Pillow and scaled down (LANCZOS) to 16, 32, 48 and 128 px, by a scratch script that wasn't kept (2026-11-14). Redraw with the same description if it's ever changed.
- **Review of step B (2026-11-14, code-review skill, high), left as they are** (no case seen): two clicks with no window open, faster than a window starts listening (a double-click), can open two windows, and the second gets no later links (fits the Someday candidate above: a second window hands its link to the first and closes); a Python path with characters outside the OEM code page makes `install` fail with UnicodeEncodeError, and a `%` in it is expanded by cmd.exe; an exception other than a bad message or OSError (e.g. deeply nested JSON) ends the helper without a reply, so Chrome shows "Native host has exited."; the 64 KB limit counts the whole JSON message, not just the link; no `CREATE_BREAKAWAY_FROM_JOB` for the window, since Chrome's launch code sets no job object (see above; the hand test checks it); `install` doesn't check that `pythonw.exe` is next to the Python it writes into host.bat; the cmd.exe test reaches the real pipe if its link ever became a web page's (it is a `chrome://` link on purpose). Fixed: a too-long docstring line in app.py, and `host.open_window` renamed `start_window` (a parameter had the same name).
