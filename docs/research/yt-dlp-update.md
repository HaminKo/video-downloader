# The built app updating yt-dlp itself (To do 21)

Started 2026-11-14 (To do 21, questions and plan). Marked by how each fact is known: read (in code or docs), measured (run on this PC), or general knowledge (not checked).

## yt-dlp's own updater (read 2026-11-14, yt-dlp 2026.10.26, `yt_dlp/update.py`)
- **It refuses the built app:** a PyInstaller app whose `sys._MEIPASS` is `<exe folder>\_internal` counts as the variant `win_dir`, and `_NON_UPDATEABLE_REASONS` says for it "Auto-update is not supported for unpackaged executables; Re-download the latest release". The bundled yt-dlp is pip's anyway: its `version.py` has `VARIANT = 'pip'` and an `UPDATE_HINT` ("Use that to update"), which `is_non_updateable()` returns first. So `Updater(ydl).update()` can't be used; the app needs its own few steps.
- **What it does where it does update**, worth doing the same way:
  - The newest version: `GET https://api.github.com/repos/yt-dlp/yt-dlp/releases/latest` (headers `Accept: application/vnd.github+json`, `User-Agent: yt-dlp`, `X-GitHub-Api-Version`); its `tag_name` is the version.
  - A release's files: `https://github.com/yt-dlp/yt-dlp/releases/download/<tag>/<name>` (`latest/download/<name>` for the newest).
  - GitHub can answer 200 with an HTML error page (yt-dlp issue 17550): it checks the first 512 bytes for `<!DOCTYPE html>`.
  - `_update_spec`, a small file in each release: lines `lock <tag> <regex>` (or `lockV2 <repo> <tag> <regex>`) matched against `"<variant> <system_identifier()>"`, which holds the Python version and Windows version; a match caps the update at that tag (for Pythons or systems a newer yt-dlp no longer supports). **More detail (read 2026-11-15, To do 22, `_process_update_spec()` and `_download_update_spec()`):** when any `lockV2` line is there, only `lockV2` lines for the requested repo count (`yt-dlp/yt-dlp` for stable), else only `lock` lines; `re.match()` (anchored at the start only), the first matching line wins and gives its tag. The spec is fetched only when there is an update, from `latest`. **A 404 for `_update_spec` stops the update** ("The requested tag ... does not exist", no update), as does any other error fetching it; To do 22's file had said it falls back to the latest, which was wrong. The identifier is `f'{detect_variant()} {system_identifier()}'`, e.g. `zip Python 3.13.1 (CPython AMD64 64bit) - Windows-11-... (OpenSSL ...)`.
  - yt-dlp itself refuses an old Python at import: 2026.10.26's `yt_dlp/__init__.py` starts with `if sys.version_info < (3, 11): raise ImportError(...)` (read 2026-11-15). So a release too new for the app's Python fails the app's import check in `use_newest()`.
  - The checksum: `SHA2-256SUMS` from the same release, one line per file, the SHA-256 first and the file name last. Without it, yt-dlp warns and doesn't restart into the new version. It doesn't check `SHA2-256SUMS.sig` (the GPG signature).
  - The zipapp (`yt-dlp`, no extension; variant `zip`) is replaced in place.
- **Channels:** stable `yt-dlp/yt-dlp`, nightly `yt-dlp/yt-dlp-nightly-builds`, master `yt-dlp/yt-dlp-master-builds`.

## YouTube's scripts (yt-dlp-ejs) (read, same version, `yt_dlp/extractor/youtube/jsc/_builtin/ejs.py`)
- **Where yt-dlp gets them, in order:** the `yt_dlp_ejs` package (its comment: "PyPI, PyInstaller exe, zipimport binary, etc"; the zipapp does carry the package, measured below), yt-dlp's cache, a copy inside yt-dlp itself (`vendor/`: the core script, and the lib script only as Deno's or Bun's npm variant), and the web (only with `remote_components` `ejs:github`, which the app doesn't set).
- **Only a matching version is used:** a script's major.minor must equal yt-dlp's `vendor.VERSION` (0.8.0 in 2026.10.26) and its hash must be in `vendor.HASHES`. So a newer yt-dlp that expects a newer EJS version skips the bundled `yt_dlp_ejs` 0.8.0 and falls back to its own copy. Whether that copy works with Deno here (the npm variant, which Deno would fetch from npm) is not checked, and no longer matters: the zipapp brings its own matching `yt_dlp_ejs` (below).

## The built app (read 2026-11-14 in `dist\Video Downloader\_internal`)
- **No `yt_dlp-*.dist-info`** in the build (only websockets'), and yt-dlp's modules are inside the .exe's module archive. So `importlib.metadata` can't tell the bundled version, and `import yt_dlp.version` first runs `yt_dlp/__init__.py`, which loads the whole bundled yt-dlp. - **The app loads yt-dlp at once:** `app.py` imports `downloader`, which imports `yt_dlp`, and `installer/start_app.py` imports `app`. A downloaded copy must be on `sys.path` before that import.

## Parts a newer yt-dlp might miss (measured 2026-11-14)
- **Python's standard library:** the built app lacks 48 of its modules (most of them development tools or Unix-only: `unittest`, `pdb`, `zoneinfo`, `graphlib`, `difflib`, `smtplib`, `compileall`, `fcntl`, ...). The static imports of 10 zipapps from 2023.11.16 to 2026.10.26 (about one per 4 months) added 5 standard-library modules over those 3 years (`glob`, `textwrap`, `secrets`, `array`, `sysconfig`), all of them in the bundle. The only lacking one any of them imports is `fcntl` (Unix only, guarded), in all ten. So no case in 3 years; bundling the whole standard library isn't needed (and the import check falls back if it ever happens).
- **The bundled packages stay at the build's versions** (read in yt-dlp 2026.10.26): its network code turns a handler off when a package is too old (`urllib3 < 2.0.2`, `websockets < 13.0`; the bundle has 2.8.0 and 17.4), and `certifi` (the list of trusted certificate authorities) ages until a new Setup. None of this stops the import.

## Step B: the updater as built (2026-11-14)
`src/video_downloader/ytdlp_update.py`; tests in `tests/test_ytdlp_update.py` (a web server on this PC as GitHub, a tiny fake yt-dlp as the release).
- **How it runs:** `installer/start_app.py` calls `use_newest()` before importing the app; `main()` starts `check()` in a daemon thread once the window is built (not before: the download and the about 5 s of compiling would compete with building the window; the review's finding). Only in the built app.
- **Choosing a copy:** the copies are folders in the app folder's `yt-dlp\` named like a version (`2026.10.26`, or `2026.1.5` as pip writes the bundled one; compared as numbers). `use_newest()` tries the usable ones newest first (newer than the bundled yt-dlp, not in the notes' failed list), importing `video_downloader.downloader` with each, so a release that renamed `CookieLoadError` or `DownloadCancelled` fails the check too. After a failure it tries the next copy, and last the bundled yt-dlp (step A planned only the bundled one; the copy in use before an update is kept anyway, so it comes first).
- **The notes:** `yt-dlp\update.json`: `checked` (when GitHub last named its newest release; a failed request doesn't count, so a start without internet asks again at the next start), `failed` (versions that failed to import, unpack or compile; never downloaded again) and `error` (the last check's error as text, cleared when GitHub answers). Written as a new file, then renamed over the old one.
- **Deleting:** `clean_up()`, at every start of the window, deletes every folder named like a version (or `VERSION.partial`) except the copy in use and the newest usable one. Files, other names and links (symlinks, junctions) are never touched, and only folders directly inside `yt-dlp\`. A complete copy is renamed to `VERSION.partial` first and only then deleted, so if Windows keeps some files, what is left never looks like a complete copy (the review's finding). **Measured (in the tests):** on Windows, a folder with a file open in it (Python's `open()`) can't be renamed, so such a copy stays whole until the next start.
- **HTTPS:** every redirect from an HTTPS link must go to another HTTPS link, at every step (`HttpsOnly`, the redirect handler of `fetch()`'s opener). The first version only compared the final link's scheme, which an `https -> http -> https` chain would pass (the review's finding). The User-Agent is Python's own (`Python-urllib/3.13`); GitHub answered it.
- **Renaming the finished copy:** tried 10 times, 0.5 s apart, on `PermissionError` (an antivirus program reading the new files could hold them; general knowledge, the review's finding). Whether it ever retried in the runs below: not checked.
- **Left as they are** (the review's notes): a second start that only hands its link to the open window also runs `use_newest()`, and if a copy fails there, its notes and the window's check could overwrite each other (the failed mark or the check's time lost once; the next start writes it again). The compiling holds Python's lock for each file, so the window may stutter on the day of an update (not measured).

## Step D: Restart now (2026-11-15)

## To do 22: following `_update_spec` (2026-11-15)
Decision and what was rejected: docs/decisions.md, 2026-11-15 "`_update_spec`".
- **How:** `update()` asks for the newest release as before; when it is `newer()` than the bundled yt-dlp and every copy, `locked()` fetches that release's `_update_spec` and gives the lock's tag for this Python, else the newest. That one is downloaded if it is newer too and not in `failed`. The failed check comes after `locked()` (the review's finding): a newest that failed may need a newer Python, and its spec may name the last release for this one. `newer()` leaves out copies in `failed` (the review of 2026-11-16): `use_newest()` marks a copy failed at start, but its folder stays until `clean_up()`, which runs after `update()`, so counting it put the locked release off by a day (for good if the folder couldn't be deleted). The test for a failed newest now has its folder on disk; without the fix it failed. A lock tag must look like a version (it becomes a folder name and part of a link) and only ever lowers the version; a line without a pattern, or with one Python can't compile, is skipped.
- **The identifier:** `identifier()` builds `zip ` plus yt-dlp's `system_identifier()` text, without the C library part (`platform.libc_ver()`, read in Python 3.13's `platform.py`: without `os.confstr`, as on Windows, it reads `sys.executable` through in 16 KB chunks, here the 11 MB `Video Downloader.exe`; it gives nothing on Windows). **Measured** on this PC (the `.venv`): `zip Python 3.13.1 (CPython AMD64 64bit) - Windows-11-10.0.26300-SP0 (OpenSSL 3.0.15 3 Sep 2024)`, the same as yt-dlp's (a test compares them), 0.16 s the first time (`platform.platform()`).
- **Errors:** a 404 counts as no lock (yt-dlp itself stops there: "yt-dlp's own updater" above). GitHub's HTML error page (`<!DOCTYPE html>` in the first 512 bytes, as yt-dlp checks) and every other failure stop the update for the day, written into the notes' `error`.
- **Measured against the real GitHub** (2026-11-15, from the project): `locked("2026.10.26")` gave `2026.10.26` (no lock for 3.13) in 0.27 s; with a Python 3.10 identifier, `2026.10.21`.
- **Tests:** tests/test_ytdlp_update.py, on the local fake GitHub: the line kinds (`lockV2`, `lock`, any build, the first match), lines that change nothing (another Python, build or channel, `lock` beside `lockV2`, a newer tag, not a version, no pattern, a broken pattern, no spec), the locked release already here or failed, a failed newest, a cut-off spec and an HTML page, the identifier, and lines of the real 2026-11-15 spec (3.13 and 3.11 the newest, 3.10 2026.10.21, 3.9 2025.10.14, 3.8 2024.10.22, 3.6 2022.08.18.36).
- **Start time:** the module now imports `platform` (8 ms with what it loads, measured with `-X importtime`) and `ssl` (which `urllib.request` loaded before). yt-dlp imports both too, so a start loads nothing more in total.
- **Not checked:** the built app (the change is in `ytdlp_update.py` only, which the build already has; `platform` and `ssl` are bundled for yt-dlp anyway), and a real lock for Python 3.13 (none exists yet).
- **Left as they are** (the review's notes): a failed spec download says only e.g. `HTTPError: HTTP Error 503` in the notes, not which file, as for `SHA2-256SUMS` and the zipapp; when the newest has failed, its spec is fetched again each day (2.8 KB) until a newer release comes.
- **When yt-dlp writes a lock** (measured 2026-11-16, GitHub's API for release 2026.10.26, the first without Python 3.10): its `_update_spec` was uploaded in the same second as the zipapp (22:25:12Z, 14 s before the release was published) and never replaced (`updated_at` = `created_at`), and it holds the 3.10 lock. So the lock comes with the release that drops a Python; the app reads it at its first check and never downloads the release it can't use. "The newest failed" above is for a yt-dlp that forgets this once. One release looked at, not a rule.
- **Left as they are** (the review of 2026-11-16, Claude's suggestion): a locked release that fails once, even by chance (an antivirus holding a file), stays in `failed`, and no later release replaces it, so the app keeps the copy before it until a new Setup (needed then anyway, for a newer Python). Once locked, the spec is fetched and `identifier()` runs every day (docs/decisions.md, `_update_spec`). docs/using.md's "whether there is a newer version, and if there is, downloads it" stays: the locked release is newer than what the app has.

The installed 0.1.1's `_internal` has `_wmi.pyd`, which `platform.platform()` uses, and its `update.json` showed a check without error (2026-11-15). docs/todo.md's "Where we are" says what to look at after the next yt-dlp release.
