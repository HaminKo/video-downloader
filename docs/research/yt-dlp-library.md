# yt-dlp as a library: settings, hooks and what they report

Found while building To do 3, step A (2026-11-11), with yt-dlp 2026.10.26. "Read in the source" means read in `.venv/Lib/site-packages/yt_dlp`; "measured" means run on this PC (tests/test_downloader.py downloads a 1-second clip from a web server on this PC).

## Settings
- **The `-t mp4` and `-t mp3` presets** (read in the source, `_PRESET_ALIASES` in options.py) convert to these library options (measured with `yt_dlp.parse_options(["--ignore-config", "-t", "mp4"]).ydl_opts`, compared with no options):
  - mp4: `format_sort` `vcodec:h264,lang,quality,res,fps,hdr:12,acodec:aac`, `merge_output_format` and `final_ext` `mp4`, postprocessor `FFmpegVideoRemuxer` to mp4.
  - mp3: `format` `ba[acodec^=mp3]/ba/b`, `final_ext` `mp3`, postprocessor `FFmpegExtractAudio` (`preferredcodec` mp3, `preferredquality` "5", `nopostoverwrites` False).
  - Both also add `FFmpegConcat` (`only_multi_video`, `when: playlist`); left out (it joins a "multi-part" video on a few sites into one file; no case seen, decided in To do 8). `test_settings_are_yt_dlps_own_presets` fails if a yt-dlp update changes the presets.
- **`final_ext` matters for "already there"** (read in the source, `existing_video_file` in YoutubeDL.py): yt-dlp looks for the finished file under `final_ext`. Without it, an existing `Title.mp3` isn't found and the audio is downloaded and converted again.
- **`playlist_items: "1"`** with `noplaylist: True`: a watch link with `&list=` gets just the video, a playlist or channel link only its first video. Tried with a real YouTube playlist link in the user's test of To do 3, step B: only the first video was downloaded. **Replaced in To do 8, step B (2026-11-14):** `playlist_items` is gone, so a playlist gets all its videos; `noplaylist` stays (see "Playlists and channels").
- **`color`**: yt-dlp puts terminal color codes into its error messages when the terminal supports them. `{"stdout": "never", "stderr": "never"}` turns them off. A plain string (`"never"`) also works at runtime, but pyright's stub accepts only the dict form.
- **Types:** pyright bundles stubs for yt-dlp (typeshed's `types-yt-dlp`). The settings type is `yt_dlp._Params`, a TypedDict that exists only for type checking: import it under `if TYPE_CHECKING:` and write it in quotes. Its hooks take `Mapping[str, Any]`, so our hook functions must too.
- **File dates:** with the library's defaults (`updatetime` unset), files get the download time as their date, not the upload date. The command line sets `updatetime` only with `--mtime` or the `mtime-by-default` compat option (read in `__init__.py`).

## Quality: a height limit in `format_sort` (To do 6, 2026-11-11)
- **How a limit works** (read in the source, `FormatSorter` in utils/_utils.py): `res:720` prefers the largest `res` up to 720, and if there is none, the smallest above it. `res` is the smaller of width and height, so a portrait 1080x1920 video counts as 1080. Fields are compared in list order, and only a field's first appearance counts: a later `res:720` after a plain `res` does nothing.
- **The trap: `quality` comes before `res` in the mp4 preset**, and YouTube sets `quality` from its own labels (hd720, hd1080...; read in extractor/youtube/_video.py). So writing `res:720` in place of `res` still picks 1080p: measured on two videos, every limit (1080, 720, 480) gave the same 1080p file. The limit has to come before `quality`.
- **Where to put it:** right after `vcodec:h264` (H.264 still wins over the height) or first, as yt-dlp's command line does for `-t mp4 -S res:720` (a later `-S` is put in front: `append: -1` in options.py). Both gave the same files on the two videos measured, since YouTube has H.264 at 1080, 720 and 480. They differ only on a site whose wanted height exists only in another codec: then "first" takes that codec, "after H.264" takes another height in H.264.
- **Measured 2026-11-11** with extract_info(process=False) once, then only yt-dlp's format selection per sort list (scratch script, not kept); sizes are YouTube's own figures for each format, not downloaded files:

  | Video | Best that plays everywhere (preset) | 720p | 480p | Highest (yt-dlp default) |
  |---|---|---|---|---|
  | 4K test video, about 1 hour | 1080p H.264, 2677 MB | 720p H.264, 1513 MB | 480p H.264, 562 MB | 2160p VP9, 17117 MB |
  | 10-minute tutorial | 1080p H.264, 23.0 MB | 720p H.264, 18.5 MB | 480p H.264, 14.1 MB | 1080p AV1, 17.4 MB |

  The preset gave 1080p even for the 4K video: YouTube's H.264 stops at 1080p, so a "1080p" choice would give the same file as the preset. Audio is the same in every column (AAC, 82 MB and 10 MB), which is why the tutorial shrinks so little.

## Hooks
- **progress_hooks** (measured): `status` "downloading" many times with `downloaded_bytes` and `total_bytes` or `total_bytes_estimate` (HLS: `fragment_index` and `fragment_count`), then "finished". `info_dict` is the format being downloaded, so `vcodec == "none"` means audio and `acodec == "none"` means video.
- **A file that is already there** (measured, and read in `process_info`):
  - Single-file download: yt-dlp still calls the downloader, which reports "finished" (no "downloading") for the existing file.
  - Video and audio merged (YouTube): the downloader isn't called at all for an existing final file (read in the source; not yet measured, since the test clip is a single file).
- **Downloads handed to ffmpeg report only "finished"** (read in the source: `ExternalFD.real_download` in downloader/external.py). yt-dlp uses ffmpeg as the downloader for live streams, for HLS protocol `m3u8` (not `m3u8_native`), and when its own HLS downloader finds features it doesn't support ("extraction will be delegated to ffmpeg", downloader/hls.py). So the bar can't fill for those; the window shows a moving bar from the start instead.
- **How the app tells "already there"** (To do 3, step A): it lists the folder's file names before the download; the result is "already there" when the final file's name was in that list.
  - Wrong first try, replaced: "nothing was downloaded" = no progress report at all. Wrong because of the single-file "finished" report above (caught by the test).
  - Wrong second try, replaced after the code review: = no "downloading" report. Wrong for downloads handed to ffmpeg, which report only "finished".
- **post_hooks** get the final file's path, also when the file was already there (read in the source, measured).
- **postprocessor_hooks**: "started" and "finished" per step; `postprocessor` is the step's name (`Merger`, `ExtractAudio`, `VideoRemuxer`, `MoveFiles`, ...). Measured: `ExtractAudio` reports "started" twice per run, and also runs (and reports) when the MP3 was already there, so the window shows "Converting to MP3..." for a moment before "Already there".

## Cancelling a running download (To do 13, 2026-11-12)
- **yt-dlp has no stop call.** Its own way is to raise `yt_dlp.utils.DownloadCancelled` from a hook (the `match_filter` docs in YoutubeDL.py say so for that hook). Read in the source: `_handle_extraction_exceptions` re-raises it, `process_info` doesn't catch it (it only catches network errors, `OSError` and `ContentTooShortError`), `run_pp` only catches `PostProcessingError`. So it comes out of `extract_info()` as itself, not as a `DownloadError`.
- **Where it can be raised** (measured with a probe script on the test clip): in `progress_hooks` (several reports a second while downloading; HTTP downloads report every block) and in `postprocessor_hooks` ("started" and "finished" of each step). A step that ffmpeg runs (joining, converting to MP3) can't be stopped in the middle: yt-dlp waits for ffmpeg with `Popen.run` / `proc.wait()` and only stops it on Ctrl+C in the main thread (read in the source, postprocessor/ffmpeg.py and downloader/external.py). Raising at "finished" stops after the step.
- **What is left behind** (measured):
  - HTTP download stopped at the first report: `clip.mp4.part`.
  - HLS download (yt-dlp's own fragment downloader): `clip.mp4.part`, `clip.mp4.part-Frag1.part`, `clip.mp4.ytdl`.
  - MP3 stopped at ExtractAudio "finished": `clip.mp4` (the download) and `clip.mp3` (the conversion); yt-dlp hadn't deleted the download yet.
- **The HLS `.part` stays open after the error** (measured): yt-dlp's fragment downloader doesn't close it when a hook raises, and Windows refuses to delete an open file (`PermissionError`), also after the `except` block has ended. A `gc.collect()` after the `except` block frees it (a reference cycle holds it); then it deletes. HTTP downloads close their file (`close_stream()` in downloader/http.py). The test `test_cancel_deletes_what_the_download_saved[HLS]` fails without the `gc.collect()` (checked by taking it out: WinError 32).
- **No hook runs during the lookup, nor during a download handed to ffmpeg** (read in the source; see "Downloads handed to ffmpeg report only 'finished'" above): Cancel then waits until the first report (lookup: seconds) or until that whole download ends. A live stream never ends, so there Cancel does nothing; only closing the window stops it (as before To do 13). Not fixed: no case seen.
- **ExtractAudio reports "started" twice before ffmpeg runs** (measured), so Cancel clicked at the first "Converting to MP3..." stops at the second "started", before the conversion. Cancel clicked once ffmpeg is running waits for "finished".
- **Every file of a download starts with the title's file name and a dot** (measured above, and read in the source): `info_dict["_filename"]` (in every hook's `info_dict` for the video, e.g. `clip.mp4`) without its extension, then `.`: format files `Title.f137.mp4`, `.part`, `.ytdl`, `-Frag`, `Title.temp.mp4` while joining, subtitles `Title.en.srt`. A subtitle download's `info_dict` has no `_filename`; its status `filename` (`Title.en.vtt`) does.

## Files yt-dlp deletes
- **An MP3 download deletes an MP4 of the same video that was there before, when the site has no separate audio** (measured 2026-11-12 with the test clip: MP4 download, then MP3 into the same folder; afterwards only `clip.mp3` was left). Why (read in the source): the MP3 preset's format `ba[acodec^=mp3]/ba/b` falls back to `b`, the file with video and sound, named `Title.mp4`; yt-dlp finds `Title.mp4` "already downloaded", converts it, and `FFmpegExtractAudioPP` hands it back for deletion, which `run_pp` does unless `keepvideo` is set. On YouTube the audio is a file of its own (`Title.m4a` or `Title.webm`), so it shouldn't happen there (not measured). Found in To do 13; fixed in To do 14 as below (docs/decisions.md).
- **`keepvideo: True` keeps it** (measured 2026-11-12, To do 14, scratch probe on the test clip, not kept): MP4 then MP3 into one folder left `clip.mp3` and `clip.mp4`, the MP4 byte for byte unchanged; without it only `clip.mp3`, as above. The cost: an MP3 downloaded on its own also leaves its source (`clip.mp4` next to `clip.mp3`), so the app has to delete that itself. `keepvideo` does nothing else in the library (read in the source: only `run_pp` reads it; the command line's `__init__.py` also uses it to pick a default format, which our explicit `format` overrides).
- **The ExtractAudio hook names the file converted from** (measured): `info_dict["filepath"]` is the source at "started" and at "finished" (both report a copy made before the step), e.g. `clip.mp4`. When the MP3 was already there it is `clip.mp3` itself, which must then not be deleted.
- **Known gaps of the fix, left alone (no case seen; found by To do 14's code review, read in the source):**
  - A downloaded `Title.mp3` whose sound isn't MP3 (a site naming it wrong): ExtractAudio renames it to `Title.orig.mp3` and hands that back for deletion. With `keepvideo` it now stays, since the hook names only `Title.mp3`.
  - A conversion that fails leaves a new source (e.g. `Title.webm`), as yt-dlp did before the fix too: the app deletes sources only after a finished download.
- **Ways that don't help** (read in the source): `paths: {"temp": ...}` doesn't, since `existing_video_file` also looks for `Title.mp4` in the home folder and converts that one in place. A format without the `/b` fallback (`ba[acodec^=mp3]/ba`) would make MP3 fail on every site with no separate audio, the test clip's included.

## Playlists and channels (To do 8, 2026-11-12)
Found while planning To do 8: read in the source (yt-dlp 2026.10.26), and the file names measured offline with `YoutubeDL.prepare_filename` (scratch probe, not kept).
- **yt-dlp lists the whole playlist first** (read, `__process_playlist` in YoutubeDL.py): `list(entries)` unless `lazy_playlist` is set, so the number of videos (`n_entries`) is known before the first one starts, but a big channel is paged through completely first, and no hook runs meanwhile (Cancel can't act then).
- **Per entry** (read): `match_filter` is called with `incomplete=True` before each entry is looked up, with `n_entries`, `playlist_autonumber` (1, 2, ... in download order), `playlist_index` and the playlist's own fields (`playlist_title`, `playlist_id`, ...). The same fields are in every hook's `info_dict` for that video. `match_filter` may raise `DownloadCancelled` to stop everything (documented in YoutubeDL.py).
- **One failure ends the whole download unless `ignoreerrors` is set** (read): the library's default (False) turns an error into a `DownloadError`. The command line's default is `"only_download"` (`--no-abort-on-error`: "continue with next video on download errors"). With it, yt-dlp reports the error and goes on, and `extract_info()` returns None when the link itself fails. `DownloadCancelled` and `CookieLoadError` still come out as themselves (`_handle_extraction_exceptions`).
  - So with `ignoreerrors` the app learns about failures only from their texts. A `logger` setting (any object with `debug`, `warning` and `error`) gets them (read, `to_screen`, `to_stderr`, `report_warning`): errors with their "ERROR: " prefix, warnings without "WARNING: ", and everything `to_screen` prints goes to `debug`, also with `quiet`.
  - **Built in To do 8, step A (2026-11-14; read in the source, checked by the existing tests):**
    - `logger.error` gets everything yt-dlp prints to stderr, not only errors: a bare `"\r"` (`ReExtractInfo`), "Deprecated Feature: ..." (which also goes to `logger.warning`, so it is printed twice), tracebacks with `verbose`. Only lines starting "ERROR:" are errors (`report_error` adds it; plain with `color: never`). `only_once` is ignored with a logger. Progress lines go to `debug` unless `noprogress` (set), which wins.
    - For one video, the first "ERROR:" line has exactly the text the `DownloadError` had without `ignoreerrors` (`trouble()` raised at the first one), so the plain messages are unchanged.
    - A broken sign-in file still raises, as `CookieLoadError` (from `yt_dlp.cookies`, not a `DownloadError`): `cookiejar` reports the cause as an error ("... does not look like a Netscape format cookies file") and re-raises; without `ignoreerrors` the report itself raised a `DownloadError`. The `with` block's close raises it a second time (`save_cookies()`), so the log has the error twice (measured with a scratch probe, not kept). It is the one failure that still raises: `trouble()` never raises with `ignoreerrors`, and the extraction wrapper (`_handle_extraction_exceptions`) reports every other exception, the app's own hook errors included, as an "ERROR:" line.
    - The generic extractor's "Falling back on generic information extractor" is a warning (printed); "There are no subtitles for the requested languages" goes through `to_screen`, so with `quiet` or the logger it isn't printed (measured with a scratch probe on the test pages).
    - A subtitle download that fails still stops the video with `"only_download"` (`_write_subtitles` raises a `DownloadError` unless `ignoreerrors is True`), which the extraction wrapper then reports as an error; with `True` it would only warn and save the video without them.
    - A failed lookup makes `extract_info()` return None; a failed download returns the info, with no post hook called.
    - The type stub's `_LoggerProtocol` asks for more methods (`info`, `stdout`, `stderr`, an `__init__(ydl)`) than yt-dlp calls; the app's `Log` has the three it calls.
  - **Paths yt-dlp reports are normalized** (read, `sanitize_path` in utils/_utils.py): on Windows every path goes through `os.path.normpath`, so `..` is collapsed and the folder's own text can differ from `paths: {"home": ...}` when that has `..` or is relative. download() therefore passes `os.path.abspath(folder)` and compares with that. A folder name ending in a dot or space would be changed to `#` (read, not measured: the download goes elsewhere, and the app deletes nothing there, as it is outside the folder).
- **Built in To do 8, step B (2026-11-14):**
  - **When `match_filter` is called** (read, `_match_entry`, `__process_playlist`, `process_video_result`, `process_info` in YoutubeDL.py):
    - Once for the playlist itself, with its fields but no `n_entries` (`common_info` has no `_type`, so it counts as a video), before the listing.
    - Per entry before its lookup (`incomplete=True`), only when the entry is a video or a `url` entry whose extractor's `is_single_video()` is True. YouTube's video entries: yes. The generic extractor, Reddit and X have `_RETURN_TYPE` "any", so `is_single_video()` gives None and the call is skipped. Playlist entries (a channel's tabs) never get it.
    - Twice after every video's lookup: in `process_video_result` (`incomplete=self._format_fields`, a non-empty set, so truthy) and in `process_info` (False). In a playlist both carry `n_entries` and `playlist_autonumber` (from `extra`).
    - So the app counts a video once per (`playlist_id`, `playlist_autonumber`), and counts the playlist's size from `n_entries`, not from the calls (a failed lookup on Reddit gets no call at all). Found by the code review; the first version counted calls.
  - **`DownloadCancelled` from `match_filter` stops everything** (read): `_match_entry` catches it and, since `params["match_filter"]` is set (its `break_opt`), raises a new `DownloadCancelled`, which `_handle_extraction_exceptions` passes through. Measured: Cancel between two videos (`test_cancel_during_a_playlist_keeps_the_videos_finished`).
  - **The post hook runs after all of a video's steps** (read, `process_info`: after `post_process`, which ends with `MoveFiles` and the "after_move" steps). An error in it is reported as "post hooks: ..." and the video counts as not finished, so the app's post hook must not raise.
  - **The local two-video page** (measured, tests/test_downloader.py): the playlist is named after the page title ("Two clips"), its videos "Two clips (1)" and "Two clips (2)" (the generic extractor numbers entries when there are several, and returns a plain video when there is one, so no "playlist of one" there). A missing file fails only its own download (HTTP 404), and the next video still comes. When both are missing the empty "Two clips" folder stays (yt-dlp made it).
  - **Two videos with the same title** (measured, `test_a_video_named_like_one_finished_before_it`): yt-dlp takes the second for the first's file ("already downloaded"), and for MP3 still runs ExtractAudio on it. Its prefix is the first video's, so a Cancel during it deleted the first video until a finished video's files joined the "there before" set (found by the code review; the test fails without that).
- **Built in To do 8, step C (2026-11-14):**
  - **A channel's tabs aren't asked about, only their videos** (read again, yt-dlp 2026.10.26, after a code review said a home link's list of tabs would also reach `confirm` with the number of tabs): `check_filter` in `_match_entry` returns before `match_filter` for `playlist` entries and for `url` entries whose extractor's `is_single_video()` isn't True (YouTube's tab entries), and a tab's own call (`common_info`, strict) has no `n_entries`. So `confirm` comes once per tab, with that tab's video count.
  - **The box on a minimized window** (tested by the user): a download sent from Chrome to a minimized window brings it up with the box, after the listing (NASA's Videos tab).
- **yt-dlp's own failure count misses failed downloads** (read): `__process_playlist` counts an entry as failed only when its lookup fails. `process_video_result` returns the video's info also when `process_info` couldn't download it.
- **post_hooks can't stop a download** (read, `process_info`): an exception from a post hook is caught and reported as an error ("post hooks: ..."). A post hook runs once per video, after all its steps (joining, converting, moving).
- **A YouTube channel's home link is several playlists** (read, extractor/youtube/_tab.py): `youtube.com/@name` gives one playlist per tab (Videos, Shorts, Live), each with its own entries and `playlist_title`; yt-dlp prints "Downloading as multiple playlists, separated by tabs". A tab's own link (`/videos`) gives just that tab.
- **A subfolder per playlist** (measured): `%(playlist_title|.).80B/%(title).150B.%(ext)s` puts a playlist's videos into a folder named after it (cut to 80 bytes), and a single video (no `playlist_title`) straight into the download folder: the `.` default adds no folder. Characters Windows forbids are replaced as in file names (`My list: x/y?` becomes `My list： x⧸y？`).
  - Wrong first try: `%(playlist_title&{}/|)s` (the replacement syntax). The replacement is applied before the value is cleaned, so the `/` became `⧸`, part of the name instead of a folder.
  - **A playlist titled exactly `..` escapes the download folder:** its videos would land in the parent folder (Downloads). Every other odd title tried stays inside (`.` adds no folder, `...` becomes `..#`, `../x` becomes `..⧸x`, `a.` becomes `a#`). `CON` stays `CON`, a name Windows can't give a folder, so that download should fail (not measured). So the app's deleting must never reach outside the download folder.

## Errors
- With the library's defaults (no `ignoreerrors`), a failure raises `yt_dlp.utils.DownloadError`; its text starts with "ERROR: " (read in `trouble()`). A missing file on the test server gives a message with "404" in it (measured).
- **Telling errors apart needs the text** (read in the source): a private, removed or sign-in-only YouTube video is the same plain `ExtractorError`; the difference is only in the text, which for YouTube is YouTube's own "reason" text (`_video.py`, near "playerErrorMessageRenderer"). `DownloadError.exc_info` holds the original exception, but only network errors and `UnsupportedError` have their own types.
- **Texts measured 2026-11-11** with the app's own settings (yt-dlp 2026.10.26), "ERROR: " left out:
  - Not a link (`hello`): `[generic] 'hello' is not a valid URL`.
  - A page with no video (local page; also https://example.com/): `Unsupported URL: <link>`.
  - Missing file (local server): `[generic] missing: Unable to download webpage: HTTP Error 404: File not found (caused by <HTTPError 404: File not found>)`.
  - Unknown host (`nonexistent.invalid`): `[generic] watch?v=1: Unable to download webpage: HTTPSConnection(host='nonexistent.invalid', port=443): Failed to resolve 'nonexistent.invalid' ([Errno 11001] getaddrinfo failed) (caused by TransportError("..."))`.
  - Nothing listening (127.0.0.1 port 9): `... Failed to establish a new connection: [WinError 10061] No connection could be made because the target machine actively refused it (caused by TransportError("..."))`.
  - No internet (Wi-Fi off): exact text not recorded. Expected to look like the unknown host (getaddrinfo fails, errno 11001 or 11002; an estimate). The user's test of To do 3, step B showed the "Couldn't reach the site" message, so it matches one of those patterns.
  - YouTube private (yt-dlp's own test video yZIXLfi8CZQ): `[youtube] yZIXLfi8CZQ: Private video. If the owner of this video has granted you access, please sign in. Use --cookies-from-browser or --cookies for the authentication. See ...`.
  - YouTube removed (6SJNVb0GnPI): `[youtube] 6SJNVb0GnPI: This video has been removed for violating YouTube's policy on hate speech. Learn more about combating hate speech in your country.`
  - YouTube, no such video (`zzzzzzzzzzz`), and yt-dlp's age-restricted test video Ms7iBXnlUO8 (now gone): `[youtube] <id>: This video is unavailable`.
  - Reddit (To do 4's example): warnings `Session request failed: HTTP Error 403: Blocked`, then `[Reddit] 1xsyq9n: Account authentication is required. Use --cookies-from-browser or --cookies for the authentication. See ...`.
  - ffmpeg missing (`ffmpeg_location` set to an empty folder), MP3: `Postprocessing: ffprobe and ffmpeg not found. Please install or provide the path using --ffmpeg-location`. MP4 of a file that is already H.264 MP4: no error at all (nothing to join or convert).
- **Read in the source, not measured:** sign-in texts all end in yt-dlp's hint "Use --cookies-from-browser or --cookies ..." (`_login_hint` in extractor/common.py); YouTube's age check and bot check start "Sign in to confirm your age" and "Sign in to confirm you're not a bot"; a country block raises `GeoRestrictedError` ("...not available from your location..." or "The uploader has not made this video available in your country"). A network failure during the download itself (not while looking up the video) reads `unable to download video data: <network error>`.
- **How the app turns these into plain messages** (To do 3, step B): `PLAIN_MESSAGES` in downloader.py, text patterns checked in order, first match wins; anything else shows yt-dlp's text. Pitfalls found in the code review: a bare "unavailable" also matched `HTTP Error 503: Service Unavailable` (a passing server problem), so the pattern is "video is unavailable" / "video unavailable"; YouTube's rate limit ("Video unavailable. This content isn't available, try again later", which yt-dlp extends with "rate-limited by YouTube for up to an hour", read in `_video.py`) gets its own message before that; "sign in" and "log in" need word boundaries. **Wrong until To do 5 (2026-11-11):** the committed pattern held backspace characters where `\b` was meant (most likely written through a shell command: in To do 5, a `\\b` sent through a Bash command arrived as `\b`, which Python reads as a backspace; the Edit and Write tools keep backslashes as typed), so "sign in" and "log in" never matched; sign-in texts still got the sign-in message through yt-dlp's "--cookies" hint, but one with only a password hint (such as tenplay's "Login required to access this video") didn't. Fixed, with a test for that text.
- **Without ffmpeg, MP4 quietly gets worse** (read in `_default_format_spec`): yt-dlp can't join video and audio, so it picks the best single file with both (on YouTube often 360p) and only warns. So the app checks for ffmpeg (`shutil.which`) before it starts (To do 3, step B).
- **A page with two videos is a playlist** (measured with a local page with two `<video>` tags): `extract_info()` returns `_type` "playlist", `playlist_count` 2, and with `playlist_items: "1"` only the first is downloaded. `ydl.download()` returns no info, so the app calls `extract_info()` instead. `download()` also turned an `OSError` while saving (`UnavailableVideoError`) into a `DownloadError`; the app now catches both. **Replaced in To do 8, step A (2026-11-14):** with `ignoreerrors`, both are only logged (the extraction wrapper reports any exception as an error), so the app catches neither; it reads the first "ERROR:" line instead (see "Playlists and channels").

## Sites
- **Reddit fails without browser impersonation** (2026-11-11, the user's test of step A; reproduced with the yt-dlp command alone, so not our app):
  - What happens (read in extractor/reddit.py, seen in the warnings): yt-dlp first asks old.reddit.com for an anonymous session cookie and gets "HTTP Error 403: Blocked". Its fallback asks Reddit's newer site with browser impersonation, but `yt-dlp --list-impersonate-targets` shows every target "unavailable" (needs the `curl_cffi` package, not installed). The post's JSON then comes back as a block page, which yt-dlp reports as "Account authentication is required. Use --cookies-from-browser ...".
  - **Result (To do 4): curl_cffi doesn't fix it; Reddit blocks anyone not signed in on this network, a real browser included. curl_cffi was taken out again; only signing in could help (on the "Later" list). The steps that showed this are below.**
  - Possible ways out (before To do 4): the `curl-cffi` extra (`yt-dlp[default,curl-cffi]`, which yt-dlp's README calls "recommended"; makes its requests look like Chrome's), or signing in with browser cookies (on the "Later" list).
  - Not tested before To do 4 (tested since: it doesn't): whether `curl_cffi` fixes it. Installing it from a Claude session was refused by Claude Code's safety check as getting around a bot check, so that is the user's decision.
  - **To do 4 (2026-11-11):** the user chose the `curl-cffi` extra and installed it (`pip install -e ".[dev]"` after the pyproject.toml change), which gave curl_cffi 0.17.0 (MIT, by lexiforest; ships its own `libcurl-impersonate` DLL). Measured after that: `yt-dlp --list-impersonate-targets` lists Chrome, Safari and others with source curl_cffi, no longer "unavailable". Whether Reddit downloads now work: the user's test (pending).
  - **The user's test (2026-11-11): still blocked** with curl_cffi installed, same "Account authentication is required" (the window showed the new Reddit message). The terminal changed, though: before, two "Session request failed: HTTP Error 403: Blocked" warnings plus "attempting impersonation, but no impersonate target is available"; after, only the first warning (old.reddit.com). So the impersonated session request now goes through, and the block is on the next request.
  - Why (read in reddit.py and networking/impersonate.py): yt-dlp's Reddit code asks for impersonation only for that session request (`impersonate=True`); the request for the post itself (`www.reddit.com/<slug>/.json`) goes out as an ordinary request. The `impersonate` setting (`--impersonate chrome`) makes every request use curl_cffi as Chrome (`impersonate_preference` picks the curl_cffi handler when it has a default target). Possible causes, cheapest test first: (1) only the session request looks like Chrome: test `yt-dlp --impersonate chrome --simulate <link>` (the user runs it); (2) Reddit blocks this network for anonymous access whatever the request looks like: the post's `.json` link in an InPrivate Edge window; (3) yt-dlp's Reddit code is behind a Reddit change: 2026.10.26 is the newest release on PyPI (measured with `pip index versions yt-dlp`), and two web searches found no report of this exact failure after it, so there's nothing newer to try (a nightly build aside).
  - **Cause (1) ruled out (the user ran it, 2026-11-11):** `yt-dlp --impersonate chrome --simulate <link>`: "Setting up session via old reddit" now goes through (no warning, and no shreddit fallback, so the session cookie came back), but "Downloading JSON metadata" still gets the block page: same "Account authentication is required". Every request looked like Chrome, so how the requests look isn't the (whole) problem.
  - **Cause (2) confirmed (the user, 2026-11-11):** the post's `.json` link (`https://www.reddit.com/r/Asmongold/comments/1xsyq9n/.json`) in an InPrivate Edge window, not signed in, shows Reddit's "blocked by network security" page. So Reddit refuses that data to anyone not signed in on this network, a real browser included; yt-dlp's Reddit code reads exactly that link, so no request trick can help. Not known: whether it's this network only or all anonymous visitors. **Conclusion: curl_cffi doesn't make Reddit work here; only signing in (browser cookies, on the "Later" list) could.** Reading the post's normal web page instead of the `.json` would mean writing our own Reddit downloader, which the project rules out.
  - **To do 5 (2026-11-11): signing in** with a cookies.txt exported from the browser (docs/research/signing-in.md). **Result (the user's test, 2026-11-11): it works.** With a file holding only Reddit's cookies (15, `reddit_session` among them), To do 4's example link downloaded as MP4 in the app, on the same network that blocked it before. So the block was on anonymous access, not on yt-dlp's requests.
  - When "Account authentication is required" still shows (read in reddit.py, `_real_extract`): only when the post's JSON comes back as something else (a block page) and nobody is signed in. A private or quarantined subreddit gets its own text ("Private subreddit; ...", "Quarantined subreddit; ..."), which the app shows as the sign-in message.
