# yt-dlp as a library: settings, hooks and what they report

Found while building To do 3, step A (2026-11-11), with yt-dlp 2026.10.26. "Read in the source" means read in `.venv/Lib/site-packages/yt_dlp`; "measured" means run on this PC (tests/test_downloader.py downloads a 1-second clip from a web server on this PC).

## Settings
- **The `-t mp4` and `-t mp3` presets** (read in the source, `_PRESET_ALIASES` in options.py) convert to these library options (measured with `yt_dlp.parse_options(["--ignore-config", "-t", "mp4"]).ydl_opts`, compared with no options):
  - mp4: `format_sort` `vcodec:h264,lang,quality,res,fps,hdr:12,acodec:aac`, `merge_output_format` and `final_ext` `mp4`, postprocessor `FFmpegVideoRemuxer` to mp4.
  - mp3: `format` `ba[acodec^=mp3]/ba/b`, `final_ext` `mp3`, postprocessor `FFmpegExtractAudio` (`preferredcodec` mp3, `preferredquality` "5", `nopostoverwrites` False).
  - Both also add `FFmpegConcat` (`only_multi_video`, `when: playlist`); left out, since we download one video. `test_settings_are_yt_dlps_own_presets` fails if a yt-dlp update changes the presets.
- **`final_ext` matters for "already there"** (read in the source, `existing_video_file` in YoutubeDL.py): yt-dlp looks for the finished file under `final_ext`. Without it, an existing `Title.mp3` isn't found and the audio is downloaded and converted again.
- **`playlist_items: "1"`** with `noplaylist: True`: a watch link with `&list=` gets just the video, a playlist or channel link only its first video. Tried with a real YouTube playlist link in the user's test of To do 3, step B: only the first video was downloaded.
- **`color`**: yt-dlp puts terminal color codes into its error messages when the terminal supports them. `{"stdout": "never", "stderr": "never"}` turns them off. A plain string (`"never"`) also works at runtime, but pyright's stub accepts only the dict form.
- **Types:** pyright bundles stubs for yt-dlp (typeshed's `types-yt-dlp`). The settings type is `yt_dlp._Params`, a TypedDict that exists only for type checking: import it under `if TYPE_CHECKING:` and write it in quotes. Its hooks take `Mapping[str, Any]`, so our hook functions must too.
- **File dates:** with the library's defaults (`updatetime` unset), files get the download time as their date, not the upload date. The command line sets `updatetime` only with `--mtime` or the `mtime-by-default` compat option (read in `__init__.py`).

## Quality: a height limit in `format_sort` (To do 6, 2026-11-11)
- **How a limit works** (read in the source, `FormatSorter` in utils/_utils.py): `res:720` prefers the largest `res` up to 720, and if there is none, the smallest above it. `res` is the smaller of width and height, so a portrait 1080x1920 video counts as 1080. Fields are compared in list order, and only a field's first appearance counts: a later `res:720` after a plain `res` does nothing.
- **The trap: `quality` comes before `res` in the mp4 preset**, and YouTube sets `quality` from its own labels (hd720, hd1080...; read in extractor/youtube/_video.py). So writing `res:720` in place of `res` still picks 1080p: measured on two videos, every limit (1080, 720, 480) gave the same 1080p file. The limit has to come before `quality`.
- **Where to put it:** right after `vcodec:h264` (H.264 still wins over the height) or first, as yt-dlp's command line does for `-t mp4 -S res:720` (a later `-S` is put in front: `append: -1` in options.py). Both gave the same files on the two videos measured, since YouTube has H.264 at 1080, 720 and 480. They differ only on a site whose wanted height exists only in another codec: then "first" takes that codec, "after H.264" takes another height in H.264.
- **Measured 2026-11-11** with extract_info(process=False) once, then only yt-dlp's format selection per sort list (scratch script, not kept); sizes are YouTube's own figures for each format, not downloaded files:

  | Video | Best that plays everywhere (preset) | 720p | 480p | Highest (yt-dlp default) |
  |---|---|---|---|---|
  | 4K test video, about 1 hour | 1080p H.264, 2677 MB | 720p H.264, 1513 MB | 480p H.264, 562 MB | 2160p VP9, 17117 MB |
  | 10-minute tutorial | 1080p H.264, 23.0 MB | 720p H.264, 18.5 MB | 480p H.264, 14.1 MB | 1080p AV1, 17.4 MB |

  The preset gave 1080p even for the 4K video: YouTube's H.264 stops at 1080p, so a "1080p" choice would give the same file as the preset. Audio is the same in every column (AAC, 82 MB and 10 MB), which is why the tutorial shrinks so little.

## Hooks
- **progress_hooks** (measured): `status` "downloading" many times with `downloaded_bytes` and `total_bytes` or `total_bytes_estimate` (HLS: `fragment_index` and `fragment_count`), then "finished". `info_dict` is the format being downloaded, so `vcodec == "none"` means audio and `acodec == "none"` means video.
- **A file that is already there** (measured, and read in `process_info`):
  - Single-file download: yt-dlp still calls the downloader, which reports "finished" (no "downloading") for the existing file.
  - Video and audio merged (YouTube): the downloader isn't called at all for an existing final file (read in the source; not yet measured, since the test clip is a single file).
- **Downloads handed to ffmpeg report only "finished"** (read in the source: `ExternalFD.real_download` in downloader/external.py). yt-dlp uses ffmpeg as the downloader for live streams, for HLS protocol `m3u8` (not `m3u8_native`), and when its own HLS downloader finds features it doesn't support ("extraction will be delegated to ffmpeg", downloader/hls.py). So the bar can't fill for those; the window shows a moving bar from the start instead.
- **How the app tells "already there"** (To do 3, step A): it lists the folder's file names before the download; the result is "already there" when the final file's name was in that list.
  - Wrong first try, replaced: "nothing was downloaded" = no progress report at all. Wrong because of the single-file "finished" report above (caught by the test).
  - Wrong second try, replaced after the code review: = no "downloading" report. Wrong for downloads handed to ffmpeg, which report only "finished".
- **post_hooks** get the final file's path, also when the file was already there (read in the source, measured).
- **postprocessor_hooks**: "started" and "finished" per step; `postprocessor` is the step's name (`Merger`, `ExtractAudio`, `VideoRemuxer`, `MoveFiles`, ...). Measured: `ExtractAudio` reports "started" twice per run, and also runs (and reports) when the MP3 was already there, so the window shows "Converting to MP3..." for a moment before "Already there".

## Errors
- With the library's defaults (no `ignoreerrors`), a failure raises `yt_dlp.utils.DownloadError`; its text starts with "ERROR: " (read in `trouble()`). A missing file on the test server gives a message with "404" in it (measured).
- **Telling errors apart needs the text** (read in the source): a private, removed or sign-in-only YouTube video is the same plain `ExtractorError`; the difference is only in the text, which for YouTube is YouTube's own "reason" text (`_video.py`, near "playerErrorMessageRenderer"). `DownloadError.exc_info` holds the original exception, but only network errors and `UnsupportedError` have their own types.
- **Texts measured 2026-11-11** with the app's own settings (yt-dlp 2026.10.26), "ERROR: " left out:
  - Not a link (`hello`): `[generic] 'hello' is not a valid URL`.
  - A page with no video (local page; also https://example.com/): `Unsupported URL: <link>`.
  - Missing file (local server): `[generic] missing: Unable to download webpage: HTTP Error 404: File not found (caused by <HTTPError 404: File not found>)`.
  - Unknown host (`nonexistent.invalid`): `[generic] watch?v=1: Unable to download webpage: HTTPSConnection(host='nonexistent.invalid', port=443): Failed to resolve 'nonexistent.invalid' ([Errno 11001] getaddrinfo failed) (caused by TransportError("..."))`.
  - Nothing listening (127.0.0.1 port 9): `... Failed to establish a new connection: [WinError 10061] No connection could be made because the target machine actively refused it (caused by TransportError("..."))`.
  - No internet (Wi-Fi off): exact text not recorded. Expected to look like the unknown host (getaddrinfo fails, errno 11001 or 11002; an estimate). The user's test of To do 3, step B showed the "Couldn't reach the site" message, so it matches one of those patterns.
  - YouTube private (yt-dlp's own test video yZIXLfi8CZQ): `[youtube] yZIXLfi8CZQ: Private video. If the owner of this video has granted you access, please sign in. Use --cookies-from-browser or --cookies for the authentication. See ...`.
  - YouTube removed (6SJNVb0GnPI): `[youtube] 6SJNVb0GnPI: This video has been removed for violating YouTube's policy on hate speech. Learn more about combating hate speech in your country.`
  - YouTube, no such video (`zzzzzzzzzzz`), and yt-dlp's age-restricted test video Ms7iBXnlUO8 (now gone): `[youtube] <id>: This video is unavailable`.
  - Reddit (To do 4's example): warnings `Session request failed: HTTP Error 403: Blocked`, then `[Reddit] 1xsyq9n: Account authentication is required. Use --cookies-from-browser or --cookies for the authentication. See ...`.
  - ffmpeg missing (`ffmpeg_location` set to an empty folder), MP3: `Postprocessing: ffprobe and ffmpeg not found. Please install or provide the path using --ffmpeg-location`. MP4 of a file that is already H.264 MP4: no error at all (nothing to join or convert).
- **Read in the source, not measured:** sign-in texts all end in yt-dlp's hint "Use --cookies-from-browser or --cookies ..." (`_login_hint` in extractor/common.py); YouTube's age check and bot check start "Sign in to confirm your age" and "Sign in to confirm you're not a bot"; a country block raises `GeoRestrictedError` ("...not available from your location..." or "The uploader has not made this video available in your country"). A network failure during the download itself (not while looking up the video) reads `unable to download video data: <network error>`.
- **How the app turns these into plain messages** (To do 3, step B): `PLAIN_MESSAGES` in downloader.py, text patterns checked in order, first match wins; anything else shows yt-dlp's text. Pitfalls found in the code review: a bare "unavailable" also matched `HTTP Error 503: Service Unavailable` (a passing server problem), so the pattern is "video is unavailable" / "video unavailable"; YouTube's rate limit ("Video unavailable. This content isn't available, try again later", which yt-dlp extends with "rate-limited by YouTube for up to an hour", read in `_video.py`) gets its own message before that; "sign in" and "log in" need word boundaries. **Wrong until To do 5 (2026-11-11):** the committed pattern held backspace characters where `\b` was meant (most likely written through a shell command: in To do 5, a `\\b` sent through a Bash command arrived as `\b`, which Python reads as a backspace; the Edit and Write tools keep backslashes as typed), so "sign in" and "log in" never matched; sign-in texts still got the sign-in message through yt-dlp's "--cookies" hint, but one with only a password hint (such as tenplay's "Login required to access this video") didn't. Fixed, with a test for that text.
- **Without ffmpeg, MP4 quietly gets worse** (read in `_default_format_spec`): yt-dlp can't join video and audio, so it picks the best single file with both (on YouTube often 360p) and only warns. So the app checks for ffmpeg (`shutil.which`) before it starts (To do 3, step B).
- **A page with two videos is a playlist** (measured with a local page with two `<video>` tags): `extract_info()` returns `_type` "playlist", `playlist_count` 2, and with `playlist_items: "1"` only the first is downloaded. `ydl.download()` returns no info, so the app calls `extract_info()` instead. `download()` also turned an `OSError` while saving (`UnavailableVideoError`) into a `DownloadError`; the app now catches both.

## Sites
- **Reddit fails without browser impersonation** (2026-11-11, the user's test of step A; reproduced with the yt-dlp command alone, so not our app):
  - What happens (read in extractor/reddit.py, seen in the warnings): yt-dlp first asks old.reddit.com for an anonymous session cookie and gets "HTTP Error 403: Blocked". Its fallback asks Reddit's newer site with browser impersonation, but `yt-dlp --list-impersonate-targets` shows every target "unavailable" (needs the `curl_cffi` package, not installed). The post's JSON then comes back as a block page, which yt-dlp reports as "Account authentication is required. Use --cookies-from-browser ...".
  - **Result (To do 4): curl_cffi doesn't fix it; Reddit blocks anyone not signed in on this network, a real browser included. curl_cffi was taken out again; only signing in could help (on the "Later" list). The steps that showed this are below.**
  - Possible ways out (before To do 4): the `curl-cffi` extra (`yt-dlp[default,curl-cffi]`, which yt-dlp's README calls "recommended"; makes its requests look like Chrome's), or signing in with browser cookies (on the "Later" list).
  - Not tested before To do 4 (tested since: it doesn't): whether `curl_cffi` fixes it. Installing it from a Claude session was refused by Claude Code's safety check as getting around a bot check, so that is the user's decision.
  - **To do 4 (2026-11-11):** the user chose the `curl-cffi` extra and installed it (`pip install -e ".[dev]"` after the pyproject.toml change), which gave curl_cffi 0.17.0 (MIT, by lexiforest; ships its own `libcurl-impersonate` DLL). Measured after that: `yt-dlp --list-impersonate-targets` lists Chrome, Safari and others with source curl_cffi, no longer "unavailable". Whether Reddit downloads now work: the user's test (pending).
  - **The user's test (2026-11-11): still blocked** with curl_cffi installed, same "Account authentication is required" (the window showed the new Reddit message). The terminal changed, though: before, two "Session request failed: HTTP Error 403: Blocked" warnings plus "attempting impersonation, but no impersonate target is available"; after, only the first warning (old.reddit.com). So the impersonated session request now goes through, and the block is on the next request.
  - Why (read in reddit.py and networking/impersonate.py): yt-dlp's Reddit code asks for impersonation only for that session request (`impersonate=True`); the request for the post itself (`www.reddit.com/<slug>/.json`) goes out as an ordinary request. The `impersonate` setting (`--impersonate chrome`) makes every request use curl_cffi as Chrome (`impersonate_preference` picks the curl_cffi handler when it has a default target). Possible causes, cheapest test first: (1) only the session request looks like Chrome: test `yt-dlp --impersonate chrome --simulate <link>` (the user runs it); (2) Reddit blocks this network for anonymous access whatever the request looks like: the post's `.json` link in an InPrivate Edge window; (3) yt-dlp's Reddit code is behind a Reddit change: 2026.10.26 is the newest release on PyPI (measured with `pip index versions yt-dlp`), and two web searches found no report of this exact failure after it, so there's nothing newer to try (a nightly build aside).
  - **Cause (1) ruled out (the user ran it, 2026-11-11):** `yt-dlp --impersonate chrome --simulate <link>`: "Setting up session via old reddit" now goes through (no warning, and no shreddit fallback, so the session cookie came back), but "Downloading JSON metadata" still gets the block page: same "Account authentication is required". Every request looked like Chrome, so how the requests look isn't the (whole) problem.
  - **Cause (2) confirmed (the user, 2026-11-11):** the post's `.json` link (`https://www.reddit.com/r/Asmongold/comments/1xsyq9n/.json`) in an InPrivate Edge window, not signed in, shows Reddit's "blocked by network security" page. So Reddit refuses that data to anyone not signed in on this network, a real browser included; yt-dlp's Reddit code reads exactly that link, so no request trick can help. Not known: whether it's this network only or all anonymous visitors. **Conclusion: curl_cffi doesn't make Reddit work here; only signing in (browser cookies, on the "Later" list) could.** Reading the post's normal web page instead of the `.json` would mean writing our own Reddit downloader, which the project rules out.
  - **To do 5 (2026-11-11): signing in** with a cookies.txt exported from the browser (docs/research/signing-in.md). **Result (the user's test, 2026-11-11): it works.** With a file holding only Reddit's cookies (15, `reddit_session` among them), To do 4's example link downloaded as MP4 in the app, on the same network that blocked it before. So the block was on anonymous access, not on yt-dlp's requests.
  - When "Account authentication is required" still shows (read in reddit.py, `_real_extract`): only when the post's JSON comes back as something else (a block page) and nobody is signed in. A private or quarantined subreddit gets its own text ("Private subreddit; ...", "Quarantined subreddit; ..."), which the app shows as the sign-in message.
  - Testing it without the internet: `YoutubeDL._impersonate_target_available(ImpersonateTarget("chrome"))`, the check behind `--list-impersonate-targets` (was in tests/test_downloader.py; removed with curl_cffi). It is private (yt-dlp marks it "make available as public API" later), and pyright's bundled type file for yt-dlp (typeshed) doesn't list it, so the line needs a `pyright: ignore`.
  - The point of the Reddit test (ffmpeg joins separate video and sound) was already covered by the YouTube MP4 test, which showed "Joining video and audio...".
