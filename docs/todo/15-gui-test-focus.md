# To do 15: GUI test on another screen, without taking the keyboard (small): "have the windows show up on another screen and not take control of the computer"

- **Problem:** each GUI test window opens on top of the main screen and takes the keyboard with `focus_force()` (drive.py `focus()`). For the ~12 s the GUI test runs, the user's window loses the front and what they type is dropped. Windows also refuses `focus_force()` now and then: the "didn't get the keyboard focus" error (docs/research/gui-testing.md, seen 2026-11-12 and maybe 2026-11-13).
- **Goal:** the test windows open on a second screen with the same scaling as the main one, the keys still reach them, and the user's window keeps the front and the keyboard. Example: the user types in VS Code while `pytest tests/gui/window_gui.py` runs; everything typed lands in VS Code and the test passes. With no such screen, the windows open where they do now.
- **Read first:** docs/research/gui-test-focus.md (the probe, what was measured, what was rejected: VM, Docker, Windows containers, Windows Sandbox); docs/research/gui-testing.md "Flaky first version" (the filter tag and taking the focus back both stay); tests/gui/drive.py `open_window()`, `focus()`, `press()`, `window_frame()`; app.py `bring_to_front()` (calls `focus_force()`; the GUI test reaches it through its pipe step and `receive_link()`) and `start()` (`SetProcessDpiAwareness(1)`); the recorder for `bring_to_front` in tests/test_app.py; the user-level gui-test skill's tkinter.md.
- **Approach** (about 30-40 lines in drive.py, an estimate):
  1. `focus()`: Windows' thread-only `SetFocus(widget.winfo_id())` through ctypes instead of `focus_force()`, then `update()` and the same `focus_get()` check.
  2. `open_window()`: the first screen other than the main one with the same DPI (`EnumDisplayMonitors`, `GetMonitorInfo`, `GetDpiForMonitor`); `root.geometry("+X+Y")` a little inside its work area. Keep `-topmost` (it doesn't take the focus).
  3. Remember `GetForegroundWindow()` before the window shows; if Windows put the new window in front, `SetForegroundWindow(previous)` right after the first `update()` (Windows did it for 5 of 10 first windows in the probe).
  4. The pipe step's `bring_to_front()`: see Ask (a).
  5. Docs: CLAUDE.md "Build specifics" (the line "opens the real window on top and takes the keyboard focus"), drive.py's module text, gui-testing.md (merge gui-test-focus.md in or link it), decisions.md.
  6. Last, once the GUI test has passed several runs: update the gui-test skill's tkinter.md (its `focus_force()` advice) with this project's measurements, so future tkinter projects start with it. It's outside the repo: nothing to commit for it.
